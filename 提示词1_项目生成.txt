请在当前目录生成一个完整的、可编译运行的 Go 后端项目。

【项目模式】
本项目采用「0-1 自研生成完整项目 → 给出可注入缺陷的位置」的模式：
1. 0-1 生成项目：从零开始自行选题并完整实现一个可编译、可运行的 Go 后端项目
2. 给出缺陷注入位置：明确标注代码中可注入缺陷的位置（每个缺陷跨多个文件，逐处给出文件路径 + 函数名），并整理成缺陷候选清单，不实际植入缺陷

【选题要求】


. 大型规模：Go 代码总行数 ≥ 5000 行（不含测试代码），代码文件 ≥ 50 个 → 每个项目可提交 30 个缺陷，要求不能重复代码或者死代码等，为了凑行数进行的。

【前端页面要求】
- 项目必须包含前端页面（前端代码不计入【项目规模要求】中的 Go 代码总行数与代码文件数统计）
- 缺陷候选清单中的缺陷必须全部为后端（Go）缺陷，不能是前端缺陷

【缺陷质量硬性要求】
- 项目必须能编译通过（go build ./...）且能正常运行
- 缺陷必须是真实存在且能稳定复现的（非概率性、非语法错误），且即使注入缺陷后项目仍能编译通过并正常运行
- 缺陷必须全部为后端（Go）缺陷，不能是前端缺陷
- 所有项目与缺陷将被人工抽检，抽检不通过视为不合格
- 单文件缺陷占比不得高于 30%（即单个 .go 文件中植入的缺陷数占该项目缺陷总数的比例 ≤ 30%）
- **每一个缺陷必须**涉及并发、context 生命周期、错误传播、运行时崩溃、状态污染或跨层数据流等运行时机制（至少涉及其中任意一种），严禁纯数据变换类缺陷（如字符串归一化、大小写转换、空白处理，枚举，关键字映射，索引，边界计算，nil/空值未单独处理，其他浅层数据变换等简单，单点错误）

技术要求：
1. 纯 Go 标准库：禁止使用任何第三方依赖（不用 gin/echo/fiber 等框架，只用 net/http、sync、encoding/json 等标准库）
2. 端口 8080，API 接口：至少实现 4 个 RESTful API
3. 项目结构：
   cmd/server/main.go          — 入口文件
   internal/config/             — 配置
   internal/handler/            — HTTP handler
   internal/model/              — 数据模型
   internal/service/            — 业务逻辑
   internal/store/              — 存储层
   pkg/logger/                  — 日志
   pkg/response/                — 统一响应格式
4. 必须包含的特性：
   - 优雅关闭（监听 SIGINT/SIGTERM）
   - 健康检查端点（/health、/ready）
   - 结构化日志
   - 参数校验和错误处理
   - 合理的项目注释

缺陷候选清单生成要求：
在生成项目后，必须额外生成一个 BUG_CATALOG.md 文件，内容为该项目的缺陷候选清单。
要求：
1. 缺陷数量根据项目规模确定：标准规模 10 个，大型规模 30 个
2. 每个缺陷必须：
   - 与项目功能强相关（不能脱离业务场景）
   - 能在代码中定位到多处植入位置（每个缺陷跨多个文件，每处给出文件路径 + 函数名）
   - 触发条件明确（稳定复现，不是概率性的）
   - 缺陷之间相互独立（改动一个不影响另一个的触发）
   - 缺陷为运行时缺陷（代码能编译通过，非语法错误）
   - 缺陷为跨文件缺陷（单个缺陷的注入需同时修改至少 2 个文件，禁止仅修改单个文件中的几行代码）
3. 缺陷类型要多样化，须覆盖以下典型失效模式（其余归为 other）：
   - concurrency：data race、WaitGroup 计数错配、channel 未关闭导致 goroutine 泄露、锁的保护范围漏掉一个字段
   - nil：向 nil map 写入、nil 指针解引用、装了 nil 指针的接口与 nil 比较为假
   - slice：append 之后共享底层数组、子切片写回污染原数组、容量估算错误导致越界
   - error：%w 丢失导致 errors.Is / errors.As 失效、err 被 := 遮蔽、只比较错误字符串
   - context：取消或超时没有向下游传播、把 context 存进结构体后复用、忽略 ctx.Err()
   - defer：循环内 defer 直到函数返回才执行、defer 修改命名返回值、error 分支跳过了释放
   - other：其他不属于上述缺陷的缺陷
4. 单文件缺陷占比 ≤ 30%
5. 清单格式为表格，每个缺陷一行，包含以下字段（这些字段可直接复制到第二个提示词中）：

| 字段 | 内容 |
|------|------|
| bug_id | 唯一标识，格式：{项目缩写}-{类别}-{序号}，如 delay-concur-001 id应该从1-30 30个缺陷，这个缺陷是第几个缺陷|
| bug_category | 缺陷类别，取值：concurrency / nil / slice / error / context / defer / other |
| 运行时机制 | 该缺陷涉及的运行时机制，取值：concurrency（并发）/ context（context生命周期）/ error_propagation（错误传播）/ runtime_panic（运行时崩溃）/ state_pollution（状态污染）/ cross_layer_data_flow（跨层数据流），每个缺陷必须标注其中至少一种 |
| 缺陷描述 | 50 字内，清晰描述缺陷本质 |
| 植入位置 | 多个文件路径.函数名（用逗号分隔，至少 2 个文件），如 internal/store/memory_store.go.GetTask、internal/service/task_service.go.CreateTask |
| 预期表现 | 用户可见的错误现象，如：高并发下 panic "concurrent map read and map write" |
| 触发方式 | 如何稳定触发该缺陷的操作步骤 |
| 缺陷难度 | 1-5 星（1 最简单，5 最隐蔽） |
6. **每一个缺陷必须**涉及并发、context 生命周期、错误传播、运行时崩溃、状态污染或跨层数据流等复杂运行时机制（至少涉及其中任意一种），且验证命令必须包含 -race 和 -count=N，否则单点排序或边界错误会被直接打回。
7. **缺陷多样性要求**：缺陷之间不能过于相似，需覆盖不同的运行时机制维度。具体要求：
   - 30 个缺陷中，至少覆盖 5 种不同的运行时机制维度（并发、context 生命周期、错误传播、运行时崩溃、状态污染、跨层数据流等）
   - 同一运行时机制维度下的缺陷，触发路径和根因必须有本质区别（如不能 30 个缺陷全是 data race 的不同表现）
   - 缺陷之间的代码改动不能重叠或相互影响（即改动一个缺陷不影响另一个缺陷的触发）
Docker 评测文件生成要求：

- WORKDIR /app
- COPY 源代码到 /app
- 预先执行 go mod download 和 go build ./...
- 容器内必须保留完整 Go 工具链（能在容器内 go build、go run）
- CMD 启动服务

- 自动检查 Docker 是否可用
- 使用 docker build -f benzhi.Dockerfile
- 构建成功后给出运行示例

- 项目简介（一句话简介之后展开详细描述）
- 目录结构说明
- API 文档（每个端点的方法、路径、请求/响应格式）
- 本地运行步骤（go run ./cmd/server）
- Docker 构建和运行步骤
